## Three windows, one server

You are in a terminal, or in a side panel next to your code, or halfway through a Cascade conversation. Whichever of the three it is, she arrives the same way: one URL, no local process and no wrapper package, and the agent you already had open can put posts on your calendar.

Warp, Cline and Windsurf all speak MCP over streamable HTTP, so each one discovers her [10 tools](/mcp/tools) on connect and reads their schemas before it calls anything. The tools cover discovery, media and posting. They do not list, delete or reschedule posts that already exist, and none of them returns analytics, so that work stays on the calendar at [app.postqueen.ai](https://app.postqueen.ai) or in the [`postqueen` CLI](/cli/introduction).

<Note>
All three need your PostQueen API key. In the app at [app.postqueen.ai](https://app.postqueen.ai), open **Settings > Developers > Public API** and click **Reveal**.
</Note>

<Warning>
That key can post to every account you have connected, so treat it like a password. Whether it sits in the URL or in an `Authorization` header, it lands in a config file on your machine, so keep those files out of version control and off shared screens. If the key leaks, regenerate it in **Settings > Developers > Public API** and update every client that uses it.
</Warning>

## Warp

The deploy just finished in the window you are still looking at. Warp's agent reaches her as a URL server, so the post about that deploy gets scheduled before the log scrolls away.

<Steps>
  <Step title="Open the MCP servers page">
    Go to **Settings**, then **Agents**, then **MCP servers**. Searching for `Open MCP Servers` in the Command Palette gets you there too.
  </Step>
  <Step title="Add her as a URL server">
    Click **+ Add** and choose **Streamable HTTP or SSE Server (URL)**, not **CLI Server (Command)**, which is for local executables. Warp takes a `url` and an optional `headers` object. Both forms, with the key in the path or in a Bearer header: [Warp config](/mcp/clients/other-clients#warp).
  </Step>
  <Step title="Start the server">
    She appears in the list with a **Start** and **Stop** control. Start her, and Warp discovers the 10 tools. A server that was running when you closed Warp starts again on the next launch, and one you stopped stays stopped.
  </Step>
</Steps>

Then ask the agent for something it can act on right away:

> *"The deploy is out. Write a short post about the new export format and schedule it for tomorrow at 10am on X."*

Warp is also a terminal, so the `postqueen` CLI runs there like any other command. That route reaches the parts MCP does not cover, including `posts:list` and `analytics:platform`.

## Cline

The pull request is merged and the Cline panel is still open beside your code. Point it at her and the announcement gets written right there, with no second window and no context switch.

<Steps>
  <Step title="Open the MCP Servers panel">
    In the Cline panel, click the **MCP Servers** icon in the top toolbar.
  </Step>
  <Step title="Add her as a remote server">
    Open the **Remote Servers** tab. Name the server `postqueen`, paste the URL and pick **Streamable HTTP** as the transport, then click **Add Server**. Prefer JSON? The **Configure** tab opens the same settings file, where the entry needs an explicit `type` of `streamableHttp`. The Cline CLI reads that same shape from `~/.cline/mcp.json`. Every field: [Cline config](/mcp/clients/other-clients#cline).
  </Step>
  <Step title="Leave autoApprove empty">
    That field lists tools Cline may run without asking you first. `integrationSchedulePostTool` writes to live accounts, so it is worth a confirmation every time.
  </Step>
</Steps>

Then ask for the posts while the work is still fresh:

> *"Write posts about the new export format for LinkedIn and Bluesky, and save them as drafts."*

## Windsurf

Cascade is mid-plan, the feature is coming together, and the launch is Monday. Her tools sit in the same conversation, so the week gets planned where the work is already happening.

<Steps>
  <Step title="Open the Cascade MCP config">
    Open **Settings**, then **Cascade**, then **MCP Servers**, or click the MCP icon at the top right of the Cascade panel. The file lives at `~/.codeium/windsurf/mcp_config.json` on macOS, Linux and Windows.
  </Step>
  <Step title="Use serverUrl, not url">
    Windsurf reads remote HTTP servers from a `serverUrl` key, and getting that one wrong is the usual reason she never shows up. Windsurf also interpolates `${env:VAR_NAME}` inside these fields, so the key can stay in an environment variable instead of the file. Both forms: [Windsurf config](/mcp/clients/other-clients#windsurf).
  </Step>
  <Step title="Refresh the server list">
    Save the file, then refresh the server list in Cascade to pick up the change.
  </Step>
</Steps>

Then give Cascade a brief with a deadline in it:

> *"Plan five posts for launch week across X and LinkedIn, one per day starting Monday at 9am, and schedule them."*

## 👑 What happens after you ask

Whichever of the three you asked, the same three calls do the work.

`integrationList` comes first and returns every connected channel with its integration ID. Then `integrationSchema` asks a platform what it expects, and gets back its rules, its `maxLength` and its required settings, which is how a LinkedIn post avoids being written to X's character limit. Finally `integrationSchedulePostTool` writes the calendar entries, one item in `socialPost` per post, each with its own `date` and `integrationId`:

```json
{
  "socialPost": [
    {
      "integrationId": "your-x-integration-id",
      "isPremium": false,
      "date": "2026-08-03T09:00:00.000Z",
      "shortLink": false,
      "type": "schedule",
      "postsAndComments": [
        {
          "content": "<p>Launch week starts today. Exports now finish in seconds.</p>",
          "attachments": []
        }
      ],
      "settings": [{ "key": "who_can_reply_post", "value": "everyone" }]
    }
  ]
}
```

Content is HTML with a short list of allowed tags, and every line is wrapped in `<p>`. Attachments have to be hosted by her, so an image that lives somewhere else goes through `uploadFromUrlTool` first and the returned `path` is what gets attached. The rules in full: [tool reference](/mcp/tools).

`type` also takes `draft`. A draft is a post state rather than a queue position: it lands on the calendar and stays there, unscheduled, until you publish it from the editor at [app.postqueen.ai](https://app.postqueen.ai). Her MCP tools carry no status change, so that switch happens on the calendar or from the CLI with `postqueen posts:status <post-id> --status schedule`.

Anything scheduled needs nothing more from you. It is visible on the calendar where you can still edit or delete it, and it goes out at its time.

## FAQ

<AccordionGroup>
  <Accordion title="My client shows the server but zero tools">
    The connection worked and discovery came back empty, which usually means the key is wrong or truncated. Reveal it again in the PostQueen app and paste it in full, with no surrounding whitespace or quotes.
  </Accordion>
  <Accordion title="She never appears at all">
    Check the config key first, because it differs by client: Warp uses `url`, Windsurf uses `serverUrl`, and Cline needs `type` set to `streamableHttp`. After that, confirm the client is using streamable HTTP rather than stdio and that the trailing key segment survived the paste.
  </Accordion>
  <Accordion title="Should I let the agent run her tools without asking?">
    Keep the confirmation on for `integrationSchedulePostTool`, since that one writes to live accounts. In Cline that means leaving `autoApprove` empty. The read-only tools, such as `integrationList` and `integrationSchema`, are safe company.
  </Accordion>
  <Accordion title="Can these agents use the CLI instead of MCP?">
    Anywhere your agent can run a shell command, yes. Warp is a terminal, so the `postqueen` CLI runs there natively. The CLI is the wider surface of the two, with `posts:list`, `posts:status` and analytics that the MCP tools do not carry: [CLI introduction](/cli/introduction).
  </Accordion>
  <Accordion title="My client is not one of these three">
    Then it probably still works. Any client that can reach a remote MCP server connects with the same URL, and the generic shape, including a bridge for clients that only launch local processes, is on the [other clients page](/mcp/clients/other-clients).
  </Accordion>
  <Accordion title="Does the integration cost extra?">
    No. Agent access uses the same API key and the same plan limits as your regular PostQueen account, on any plan.
  </Accordion>
</AccordionGroup>
