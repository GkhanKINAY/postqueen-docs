The CLI signs in with an API key. One key and every command is talking to your workspace. This page matches `postqueen` 2.0.23 on npm.

## API Key

<Steps>
  <Step title="Copy your key" icon="key">
    Open [app.postqueen.ai](https://app.postqueen.ai), go to **Connections > API Keys**, and click **Reveal**. Only a workspace admin can reveal the key.
  </Step>
  <Step title="Export it" icon="terminal">
    ```bash
    export POSTQUEEN_API_KEY=your_api_key_here
    ```
  </Step>
  <Step title="Point at your own backend, if you self-host" icon="server">
    Use the same value as `NEXT_PUBLIC_BACKEND_URL`. The CLI appends `/public/v1/...` to whatever you set, and most single-domain setups serve the backend under `/api`:

    ```bash
    export POSTQUEEN_API_URL=https://postqueen.example.com/api
    ```

    <Warning>
    Leave the `/api` off and every command comes back `404`, because the request lands on the web
    interface instead of the backend. If you are unsure which shape your install has, check
    `NEXT_PUBLIC_BACKEND_URL` in your `docker-compose.yaml` and use exactly that.
    </Warning>
  </Step>
  <Step title="Prove it works" icon="circle-check">
    This is the first command that actually reaches the API:

    ```bash
    postqueen integrations:list
    ```

    <Check>
    Your connected channels come back as JSON. The key works, the URL is right, and every other
    command will reach PostQueen.
    </Check>
  </Step>
</Steps>

<Warning>
Keep the key secret: it grants full access to your workspace. An admin can rotate it any time under **Connections > API Keys**, which stops the old key working everywhere at once.
</Warning>

### What `auth:status` Tells You

```bash
postqueen auth:status
```

<Note>
`auth:status` prints which credentials the CLI found and which API URL it will use, then calls
`GET /public/v1/integrations` to prove the key still works. A revoked key fails that call. It
still exits `0` when it reports `Not authenticated.`, so scripts that need a hard gate should
use `integrations:list` instead of the exit code.
</Note>

## Environment Variables

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `POSTQUEEN_API_KEY` | Yes | - | Your PostQueen API key |
| `POSTQUEEN_API_URL` | No | `https://api.postqueen.ai` | Custom API endpoint (for self-hosted PostQueen) |
| `POSTQUEEN_AUTH_SERVER` | No | none | Only for a device-flow auth server you run yourself. PostQueen runs none, so there is no default |

## What `auth:login` Does

```bash
postqueen auth:login
```

On the hosted service the CLI signs in with an API key only, and `auth:login` makes no network call. It explains where the key is and how to set `POSTQUEEN_API_KEY`. It exits `0` when `POSTQUEEN_API_KEY` is already set, and `1` when it is not.

<Note>
Running your own device-flow auth server? `auth:login --auth-server <url>` (or `POSTQUEEN_AUTH_SERVER`)
logs in through it and saves credentials to `~/.postqueen/credentials.json`, which then take priority
over the API key. `auth:logout` removes them. Setting up that server is covered in
[server/SERVER.md](https://github.com/GkhanKINAY/postqueen-agent/blob/main/server/SERVER.md) in the
CLI repository.
</Note>
