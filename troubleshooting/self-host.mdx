## `pnpm` heap out of memory during install

The PostQueen monorepo is large enough that the default Node heap can
overflow during `pnpm install` on small VMs.

**Fix**

```bash
NODE_OPTIONS="--max-old-space-size=4096" pnpm install
```

If 4 GB is still not enough and your host has the RAM to spare, raise it
to `--max-old-space-size=8192`. Do not set the heap higher than your VM's
available memory. That just trades OOM in Node for OOM-killed by the
kernel. If you are stuck on a 2 GB VM, build the image elsewhere and
deploy the prebuilt artifact instead. See
[System requirements](/installation/system-requirements) for minimum RAM.

## `postgres ECONNREFUSED`

Backend cannot reach Postgres.

**Checklist**

1. `DATABASE_URL` host: is it `localhost` when the backend is in a
   container that does not share host networking? Use the service name
   (`postgres`) or the container IP instead.
2. Postgres ready? `docker compose logs postgres` should show
   `database system is ready to accept connections`.
3. Port mapping: if you exposed Postgres only on the Docker network,
   external `psql` will not work but the backend will. That is fine.

## "Hide a provider from the UI"

There is no env-var-based way to hide a provider from the frontend
today. The only way to do it is to set the per-organization `disabled`
field on the Integration row in the database after you connect a
channel. We are tracking the request. See the GitHub issues tagged
`enhancement`.

## Default ports

It depends on how you are running her.

**Official Docker image** (`ghcr.io/gkhankinay/postqueen-app`): the
container bundles frontend + backend and listens on a single port `5000`.
The official compose maps that to host `4007:5000`, so you reach PostQueen
at `http://localhost:4007/`.

**Running from source** (`pnpm dev` / `pnpm start`): frontend listens
on `4200`, backend on `3000` (overridable via `PORT`). Connect a reverse
proxy in front to give your users a single URL. See
[Reverse Proxies](/reverse-proxies/caddy).

Temporal listens on `7233` (gRPC) and the Temporal UI on `8080` in
either mode.

## Mounting the uploads volume

If `STORAGE_PROVIDER=local`, point `UPLOAD_DIRECTORY` at the path PostQueen
should write to, mount that path into your container, and also set
`NEXT_PUBLIC_UPLOAD_STATIC_DIRECTORY` so the frontend knows where the
files are served from. The Next.js config rewrites `/uploads/:path*` to
`/api/uploads/:path*` when local storage is active. See
[Uploads & storage](/configuration/uploads).

For multi-container deployments, either share the same volume across all
containers that need to read or write, or move to [Cloudflare R2](/configuration/r2).

## Can I deploy PostQueen on Vercel?

**Frontend:** yes, it is a standard Next.js app and deploys cleanly to
Vercel.

**Backend:** no. The PostQueen backend is a NestJS server that also embeds
a Temporal worker. It needs a long-running Node host (Fly.io, Render,
Railway, a VM, a Kubernetes pod, etc.). Serverless functions will not
work.

## Email is not sending

PostQueen sends no email at all unless `EMAIL_PROVIDER` is set to exactly
`resend` or `nodemailer`. There is no default: unset means the no-op provider.

Check that first, because it also decides activation. `EMAIL_PROVIDER=resend`
with no `RESEND_API_KEY` still counts as a provider, so new signups are created
inactive and wait for a mail that can never arrive. To use SMTP instead, set
`EMAIL_PROVIDER=nodemailer` and set `EMAIL_HOST`, `EMAIL_PORT`,
`EMAIL_USER`, `EMAIL_PASS`, `EMAIL_SECURE`. Full setup:
[Email configuration](/configuration/emails).

If no email provider is configured, user activation emails will not go
out, but PostQueen auto-activates users in that mode, so signup still
works.

## Temporal is not reachable

PostQueen schedules posts through Temporal. The backend
needs to reach the Temporal frontend on `TEMPORAL_ADDRESS`.
