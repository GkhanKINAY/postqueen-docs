## Activation link does not work

Activation links are short-lived JWTs. If you click an old one, or click
it twice, you will see one of these:

- `jwt malformed`: the link is corrupted or truncated (a mail client
  inserted a line break, or you copied only part of the URL).
- `jwt expired` / abort error on `/auth/activate`: the link has
  passed its lifetime.

**Fix**

1. Request a new activation email from the login page.
2. Copy the link directly from the email rather than typing it.
3. Open it in the same browser you originally signed up in.

## Login API returns 404 or 204

Neither `/api/health` nor `/auth/me` exists. If you went looking for them
because something suggested they were a health signal, that is why they 404.

What the frontend actually uses to decide "no session" is the `auth` cookie in
middleware, plus `GET /user/self`, which comes back empty when you are not
signed in. That is the call to watch in your network tab.

If you are logged in and `/user/self` still 404s, check
that `NEXT_PUBLIC_BACKEND_URL` matches the URL your browser is using to
talk to the backend (mismatched protocols/ports break the session cookie).

## Self-host: everyone is logged out after a restart

`JWT_SECRET` controls signing for session tokens. If you regenerate it,
every existing session becomes invalid.

<Warning>
Everyone logging in again is the mild half of what happens. Unless you have set
`ENCRYPTION_KEY`, this same value also encrypts your API keys, the OAuth client
secrets PostQueen issues, saved provider credentials and cookie logins such as
Skool. Rotating it in that state leaves those rows undecryptable, and every
connection that depends on them has to be set up again by hand.

Channels connected through a normal OAuth flow are the exception: their access
and refresh tokens are stored as the network returned them, so they survive the
rotation.

If you rotated it and your channels have gone dark, put the old value back. That
is the whole recovery. Then set `ENCRYPTION_KEY` to that old value before
rotating anything, which separates the two jobs and makes `JWT_SECRET` safe to
change. See the [Configuration Reference](/configuration/reference#encryption-key).
</Warning>

**Fix:** set `JWT_SECRET` once during initial deployment and never
rotate it lightly. Store it in a secret manager such as Doppler or
1Password, in a Docker or Kubernetes secret, or in an untracked `.env`
file on the host. **Do not commit it to version
control.** That includes "private" deploy repos, since anyone with
repo access ends up with the signing key for every session token PostQueen
has ever issued.

## Self-host: "Origin not allowed" on launches

The backend's CORS allowlist is built from `FRONTEND_URL` (and
`MAIN_URL` if set). If you access PostQueen on a hostname or port not in
that list, the backend rejects the call.

**Fix:** make sure `FRONTEND_URL` exactly matches the URL you are using
in the browser, including protocol and port.
