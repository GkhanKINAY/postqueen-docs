A Compose install keeps its data in Docker volumes. Three of them hold what no reinstall brings back, and those are what to back up before every upgrade.

## What to back up

| Volume | What it holds | Back it up |
|---|---|---|
| `postgres-volume` | The PostQueen database: accounts, workspaces, channels and their tokens, posts, settings | Always |
| `temporal-postgres-data` | Temporal's database, with the scheduled work that has not run yet | Always |
| `postqueen-uploads` | Uploaded media, while `STORAGE_PROVIDER` is `local` | With local storage. On R2 it stays empty: [back up the bucket](#if-your-media-is-in-r2) |
| `postqueen-redis-data` | Caches and counters | No, it rebuilds itself |
| `temporal-elasticsearch-data` | Temporal's search index | No, Temporal recreates it at start |
| `postqueen-config` | Nothing: the image never reads `/config` | No |

Keep your `.env` file and your edited `docker-compose.yaml` too. They are ordinary files in the folder you cloned, and `.env` holds `JWT_SECRET` and `ENCRYPTION_KEY`: a database restored without the same `ENCRYPTION_KEY` cannot read its stored secrets.

Compose prefixes each volume with the project name, the folder you cloned into, so the full names are usually `postqueen-docker-compose_postgres-volume` and so on. `docker volume ls` shows them.

## Back up

Stop the stack first, so PostgreSQL is not writing while you copy its files:

```bash
docker compose down
```

Then archive each volume with a throwaway container that mounts it at `/data` and the current folder at `/backup`:

```bash
for v in postgres-volume temporal-postgres-data postqueen-uploads; do
  docker run --rm \
    -v postqueen-docker-compose_$v:/data \
    -v "$(pwd)":/backup \
    alpine tar czf /backup/$v.tar.gz -C /data .
done
docker compose up -d
```

<Warning>
`docker compose down` stops every service in the project. On a host where other services share that project, stop the PostQueen services by name instead: `docker compose stop postqueen postqueen-postgres temporal temporal-postgresql`.
</Warning>

Copy the archives off the server. A backup on the same disk is lost with the disk.

## Restore

Replace a volume rather than unpacking over a used one, so nothing of the old contents stays underneath:

```bash
docker compose down
docker volume rm postqueen-docker-compose_postgres-volume
docker volume create postqueen-docker-compose_postgres-volume
docker run --rm \
  -v postqueen-docker-compose_postgres-volume:/data \
  -v "$(pwd)":/backup \
  alpine tar xzf /backup/postgres-volume.tar.gz -C /data
docker compose up -d
```

Repeat for the other volumes. Restore all three from the same backup, so the schedule in Temporal matches the posts in the database.

<Warning>
A PostgreSQL data folder opens only under the major version that wrote it. The Compose file runs `postgres:17-alpine` for PostQueen and `postgres:16` for Temporal: restore each archive under the same image.
</Warning>

A backup you have never restored is a guess. Try a restore on a spare machine before you need one.

## If your media is in R2

With [Cloudflare R2](/configuration/r2), `postqueen-uploads` stays empty and the bucket holds the media. The database stores only each file's address, so back up the bucket and the database together and restore them from the same moment: a database from Monday next to a bucket from Friday leaves the posts in between with missing images, and nothing reports an error.

Copy the bucket to a second bucket, for example with [rclone](https://rclone.org/s3/#cloudflare-r2):

```bash
rclone copy r2:your-media-bucket r2:your-backup-bucket/media
```

Use `copy`, not `sync`: a file deleted from the live bucket should stay in the backup. Give the backup job its own R2 token, allowed to read the media bucket and write the backup bucket, so it cannot delete the media it protects.

## Upgrade

<Steps>
  <Step title="Back up">
    Back up `postgres-volume` and `temporal-postgres-data` as above. The next step can change the database.
  </Step>
  <Step title="Move the image forward">
    With a pinned tag, raise it in `docker-compose.yaml` to a newer tag from the [app's tags](https://github.com/GkhanKINAY/postqueen-app/tags):

    ```yaml
    image: ghcr.io/gkhankinay/postqueen-app:vX.Y.Z
    ```

    With `latest`, nothing changes in the file.
  </Step>
  <Step title="Pull and recreate">
    ```bash
    docker compose pull
    docker compose up -d
    docker compose logs -f postqueen
    ```

    `up -d` recreates the containers whose image changed. Watch the log until `Backend started successfully on port 3000`.
  </Step>
</Steps>

<Warning>
**Only move forward.** Never start an image older than the one that last ran against the database: its schema step can drop the columns the newer release added.
</Warning>

### Where the schema changes

You never run a database migration by hand. Every time the container starts, it applies the image's Prisma schema before starting the app. The variable `PRISMA_MIGRATE` decides how:

| `PRISMA_MIGRATE` | What runs |
|---|---|
| Unset, empty, `false`, `False`, `FALSE` or `0` (the default) | `prisma db push --accept-data-loss` |
| Any other value, for example `true` | `prisma migrate deploy` |

`db push` makes the database match the schema, and `--accept-data-loss` lets it drop a column or table the schema no longer has, with its contents, without asking. That is why a backup comes before every upgrade, and why an older image is dangerous. The match is exact text, so `no`, `off` or `false ` with a trailing space select `migrate deploy`.

`migrate deploy` applies the repository's migrations in order instead, a `0_init` baseline and one per later schema change, and never drops what a migration does not say to. A database built by `db push` has no record of those migrations, so switching takes one step: with the current image running, and so the database matching its schema, mark every migration that image ships as applied, then set the variable and recreate the container.

```bash
docker compose exec postqueen sh -c \
  'for m in libraries/nestjs-libraries/src/database/prisma/migrations/*/; do
     npx prisma migrate resolve --applied "$(basename "$m")"
   done'
```

```env
PRISMA_MIGRATE=true
```

Marking only `0_init` is not enough on a database that already has later changes: `migrate deploy` would then try to add columns that exist and stop the start. Back up first either way.

## The command that deletes everything

<Warning>
`docker compose down -v` deletes the volumes with the containers: the database, the uploads and the scheduled work, with no prompt and no undo. Plain `docker compose down` keeps every volume. For a settings change, recreate the one container instead: see [Docker Compose](/installation/docker-compose#apply-a-change).
</Warning>
