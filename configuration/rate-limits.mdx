The routes anyone can reach without signing in (sign-in, sign-up, password reset and one-time codes) are rate limited out of the box. Nothing needs configuring for that. This page is for tightening or loosening the limits, adding a captcha, and the other hourly caps.

## Sign-in rate limits

Each protected action is counted twice over a rolling 15-minute window: once per email address and once per IP address. Whichever limit is reached first refuses further requests until the window moves on.

| Action | Name | Per email | Per IP |
|---|---|---|---|
| Requesting a one-time code | `otp_request` | 5 | 30 |
| Entering a one-time code | `otp_verify` | 10 | 60 |
| Signing in with a password | `login` | 20 | 60 |
| Signing up | `register` | 5 | 20 |
| Requesting a password reset | `forgot` | 5 | 20 |
| Changing the password | `password_change` | 5 | 20 |
| Changing the email address | `email_change` | 5 | 20 |
| Linking another sign-in method to an account | `identity_link` | 5 | 20 |

The sign-in limits are loose on purpose: they stop credential stuffing and mail bombing, and an office behind one shared address should never reach them.

With `REDIS_URL` set, as in every standard install, the counters live in Redis and are shared by every backend. Without Redis, each process counts on its own. The backend logs which at start, for example `Abuse guard using Redis counters (shared across instances)`. If Redis becomes unreachable, requests are let through rather than locking everyone out.

### Change the limits

Every number can be set. The variable is `GUARD_` + the action's name in capitals + `_EMAIL` or `_IP`:

```env
GUARD_WINDOW_MS=900000
GUARD_LOGIN_EMAIL=20
GUARD_LOGIN_IP=60
GUARD_REGISTER_EMAIL=5
GUARD_REGISTER_IP=20
GUARD_PASSWORD_CHANGE_EMAIL=5
GUARD_IDENTITY_LINK_IP=20
```

`GUARD_WINDOW_MS` is the window in milliseconds. `0` turns off that count, so `GUARD_LOGIN_IP=0` stops counting sign-ins per IP while still counting them per email.

<Warning>
A value that is not a whole number falls back to the default without a warning, so a typo keeps the old limit. Test a change rather than assume it took.
</Warning>

## Add a captcha

[Cloudflare Turnstile](https://developers.cloudflare.com/turnstile/) can be required before an action goes through. It is off until you set it up.

<Steps>
  <Step title="Create a Turnstile widget">
    In the Cloudflare dashboard, add a Turnstile widget for your domain. You get a site key and a secret key.
  </Step>
  <Step title="Set both keys">
    ```env
    TURNSTILE_SITE_KEY=your-site-key
    TURNSTILE_SECRET=your-secret-key
    ```

    Set both. The site key alone shows the widget, but without the secret nothing checks the answer.
  </Step>
  <Step title="Choose the actions it guards">
    By default only `otp_request` asks for the captcha. List others by name, separated by commas:

    ```env
    GUARD_CAPTCHA_ACTIONS=otp_request,register,forgot
    ```
  </Step>
</Steps>

## Passwordless sign-in

```env
PASSWORDLESS_LOGIN=true
```

People then sign in with a one-time code sent by email. It is compared against the exact string `true`, and it needs working [email](/configuration/emails): without a provider the codes never arrive and nobody can sign in.

## Public API and upload caps

Separate from the sign-in limits, two hourly caps apply per workspace:

| Variable | What it counts | Default |
|---|---|---|
| `API_LIMIT` | Requests to `POST /public/v1/posts`, whatever the number of posts in each. A request refused with `400` counts too | 90 per hour. The Compose file sets 30. |
| `UPLOAD_LIMIT` | Uploads. Each upload route keeps its own count | 300 per hour |

They are counted separately, so a folder of files added to the media library never uses up the posting cap. The other public API routes and posts made in the app are not counted. With Redis, the counts are shared by every backend. A request over the cap is answered with `429`: see [Limits and errors](/public-api/limits-and-errors).

## Farcaster signer routes

Connecting Farcaster uses two public routes: one creates a Neynar managed signer, the other checks whether the person approved it. Both are limited per client address, with numbers fixed in the code:

| Route | Limit |
|---|---|
| `POST /auth/farcaster/signer`, which creates a signer at Neynar | 30 per hour |
| `GET /auth/farcaster/signer`, which the approval window checks every two seconds | 1,000 per hour |

The client address is the **last** entry of the `X-Forwarded-For` header, the one added by the nginx inside the container, so a client cannot choose its own count by sending the header. Behind a reverse proxy of your own, that last entry is the proxy's address as the container sees it. Everyone then shares one count, which allows 30 new Farcaster connections per hour across the whole install.
