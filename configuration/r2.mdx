Cloudflare R2 keeps uploaded images and video in a bucket instead of on the server's disk. It is the option when you run more than one PostQueen container, or want media on a CDN address. Whether you need it at all: [Uploads and storage](/configuration/uploads).

## Before you start

| | |
|---|---|
| Account | A Cloudflare account with R2 turned on. R2 has a free tier. |
| Decision | Where media is read from: through PostQueen, a custom domain or the `r2.dev` address. See step 4. |
| Review | None |

## Set it up

<Steps>
  <Step title="Create the bucket">
    In the [Cloudflare dashboard](https://dash.cloudflare.com), open **R2 object storage** and choose **Create bucket**. Give it a name and keep the default location and the **Standard** storage class.

    <Warning>
    If your media has to stay in one region, for example the EU, choose a **jurisdiction** now. It cannot be changed later, and a bucket with one also needs `CLOUDFLARE_JURISDICTION` below.
    </Warning>
  </Step>
  <Step title="Create a token for this bucket only">
    On **R2 object storage**, open **Overview** and choose **Manage** next to **API Tokens** under **Account Details**. Create an **Account API token** with the **Object Read & Write** permission, applied to this bucket only.

    After you create it, Cloudflare shows the **Access Key ID** and the **Secret Access Key** once. Copy both, and your **Account ID** from the same page.

    <Warning>
    Do not give this token every bucket in the account. It lives in an environment variable on a web server.
    </Warning>
  </Step>
  <Step title="Set the variables">
    ```env .env
    STORAGE_PROVIDER=cloudflare
    CLOUDFLARE_ACCOUNT_ID=your-account-id
    CLOUDFLARE_ACCESS_KEY=your-access-key-id
    CLOUDFLARE_SECRET_ACCESS_KEY=your-secret-access-key
    CLOUDFLARE_BUCKETNAME=your-bucket
    CLOUDFLARE_REGION=auto
    # Only for a bucket created with a jurisdiction, for example eu
    CLOUDFLARE_JURISDICTION=
    ```

    A bucket with a jurisdiction answers only on its own endpoint, `<account-id>.eu.r2.cloudflarestorage.com`. Without `CLOUDFLARE_JURISDICTION`, PostQueen asks the account-wide endpoint and reports the bucket as missing.
  </Step>
  <Step title="Choose where media is read from">
    `CLOUDFLARE_BUCKET_URL` is the address stored with every file. Browsers load it, and several networks, Instagram, Facebook and Threads among them, download from it with their own servers. It has to be public HTTPS.

    | Option | `CLOUDFLARE_BUCKET_URL` | Trade-off |
    |---|---|---|
    | **Through PostQueen** | `https://postqueen.example.com/api/uploads` | Your own domain, and the bucket can stay private. Media leaves through your server, so it uses your bandwidth. |
    | **Custom domain** | `https://cdn.example.com` | Served by Cloudflare's edge, never touching your server. The domain has to be on Cloudflare. In the bucket, open **Settings**, and under **Custom Domains** choose **Add**. |
    | **r2.dev address** | `https://pub-<id>.r2.dev` | No setup: under **Settings > Public Development URL**, choose **Enable**. Cloudflare rate-limits it and says it is for development only. |

    <Warning>
    Never use the S3 API endpoint, `<account-id>.r2.cloudflarestorage.com`. It refuses reads without a signature, so every image breaks.
    </Warning>

    Through PostQueen, the backend reads each file from the bucket and streams it back, cached for a year. It answers only for file names PostQueen itself writes: a random name with an image, video or audio extension. Even so, keep the bucket for PostQueen media only. The `/api` in the address is required: the container's nginx serves `/uploads/` from the local disk, and only `/api/` reaches the backend.
  </Step>
  <Step title="Set the CORS policy">
    By default the browser uploads straight to the bucket, which is a cross-origin request the bucket has to allow. In the bucket's **Settings**, edit the **CORS Policy** and use your own address:

    ```json
    [
      {
        "AllowedOrigins": ["https://postqueen.example.com"],
        "AllowedMethods": ["GET", "PUT", "POST", "HEAD", "DELETE"],
        "AllowedHeaders": ["Authorization", "x-amz-date", "x-amz-content-sha256", "content-type"],
        "ExposeHeaders": ["ETag", "Location"],
        "MaxAgeSeconds": 3600
      }
    ]
    ```

    `ETag` in `ExposeHeaders` is required: the upload is sent in parts, and the browser has to read each part's `ETag` to finish it. Skip this step if you set `UPLOAD_VIA_SERVER=true`, where the browser never talks to R2.
  </Step>
  <Step title="Recreate the container">
    <RestartService />

    <Check>
    Upload an image in **Media**. It appears in the library, and the object is in the bucket.
    </Check>
  </Step>
</Steps>

Files uploaded before the switch stay where they were written, on the local disk, and keep their old addresses.

## Good to know

- **Back up the bucket and the database together.** The database stores only each file's address. Restore them from the same moment: [Backups and upgrades](/installation/backups-and-upgrades#if-your-media-is-in-r2).
- **Give backups their own token**, with read access to this bucket and write access to the backup bucket, so a backup tool cannot delete the media it protects.
- **Unfinished uploads clean themselves up.** A multipart upload that never completes leaves parts that appear in no listing. Every R2 bucket has a default lifecycle rule that aborts them after seven days.
